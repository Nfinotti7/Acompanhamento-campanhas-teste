# Reservas pelo WhatsApp — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Robô de reserva no WhatsApp (gatilho `cód. RESERVA`), motor de disponibilidade por tamanho de mesa, tela Reservas no Caixa, e pausa do robô quando um atendente responde. Primeiro cliente: Malibu (client 9, Baileys).

**Architecture:** Lógica pura (horários, vaga, leitura de texto) em serviços sem banco, testados com `node --test`. Um serviço de banco (`reservationStore.js`) grava reservas numa transação com `pg_advisory_xact_lock`. O robô (`reservationBot.js`) é chamado por `ingestWhatsAppEvent` igual ao robô da fila. O estado da conversa do robô fica numa tabela própria, `reservation_conversations`. A tabela `reservations` só guarda reservas de verdade. Isso é decisão minha, refinando o "draft" do spec. Envios do robô saem por `sendToContact` com `sentBy: 'bot_reserva'` e id de mensagem gerado antes do envio. Qualquer outra mensagem de saída pausa o robô naquele contato.

**Tech Stack:** Express ESM, Postgres (`backend/src/config/db.js`: `query` e `withTransaction`, placeholders `?`), Baileys 7.0.0-rc14, React/Vite, `node --test`.

**Spec:** `docs/superpowers/specs/2026-10-21-reservas-design.md`

## Global Constraints

- **Schema:** só aditivo, dentro de `initDb()` (`CREATE TABLE IF NOT EXISTS` / `ADD COLUMN IF NOT EXISTS`). Nunca migração separada.
- **Fuso:** Brasília = UTC-3 fixo. Horários gravados em `TIMESTAMPTZ`. Dia = `YYYY-MM-DD` de Brasília.
- **`client_id` como chave de Map/objeto em memória:** sempre `String(clientId)`.
- **Padrões de configuração:**
  - `duration_minutes` 120, `slot_minutes` 30, `hold_minutes` 15;
  - `min_advance_minutes` 120, `max_advance_days` 30;
  - `max_party` nulo = maior mesa;
  - `ad_fallback` false, `bot_enabled` true.
- **Malibu:**
  - mesas `[{seats:2,count:2},{seats:4,count:2},{seats:6,count:2}]`;
  - seg a qui: `[{start:'17:00',lastBooking:'22:30'}]`;
  - sex a dom: `[{start:'12:00',lastBooking:'14:30'},{start:'18:00',lastBooking:'22:30'}]`.
- **Textos do robô:** nunca dizem "robô", "assistente" nem "vou chamar a equipe". Quando passa pra equipe: `Só um instante, já te respondo 🙂`.
- **Pausa:** `bot_paused_until = agora + 12h`, renovada a cada mensagem do atendente.
- **Prazos do robô:** conversa de reserva sem resposta por 60 min expira. 2 tentativas sem entender na mesma etapa → passa pra equipe.
- **Frontend:** sem `#hex`/`rgba(` em `.jsx` (`theme/noHardcodedColors.test.js`). Usar variáveis CSS, mais `ResponsiveTable`/`Sheet`/`Modal` no celular.
- **Commits:** em português, terminando com `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`. Sem push sem pedido do usuário.
- **Testes:**
  - backend: `cd backend && node --test src/`;
  - frontend: `cd frontend && npm test`;
  - build: `cd frontend && npx vite build`.

## Review Focus

1. **Reserva que passa da meia-noite** (22:30 + 2h = 00:30): ela precisa ocupar a mesa no dia seguinte também. Isso vale pro cálculo e pra listagem, que busca por instante e não por data.
2. **"hoje" depois do último horário, ou dentro das 2h mínimas:** zero horários. O robô oferece o próximo dia com vaga, sem mostrar lista vazia.
3. **"sábado" dito num sábado:** é hoje, se ainda há horário; senão, o próximo sábado.
4. **Falha de envio do robô:** a linha pré-gravada com o id gerado não pode ficar como mensagem "enviada" fantasma no histórico. Deve ser marcada `failed`.
5. **Duas mensagens com o código quase juntas** (toque duplo): uma conversa só, por índice único parcial. E duas pessoas confirmando a última mesa ao mesmo tempo: uma recebe a lista atualizada.

**Interfaces:**
- Produces:
  - `DEFAULT_RESERVATION_SETTINGS`: objeto com `tables: []`, `hours: {0..6: []}` (0 = domingo), `exceptions: []`, os números de Global Constraints, `ad_fallback`, `bot_enabled`, `messages: {}`.
  - `toInstant(day: 'YYYY-MM-DD', hhmm: 'HH:MM') → Date`: UTC-3 fixo.
  - `dayOf(date: Date) → 'YYYY-MM-DD'`: em Brasília.
  - `weekdayOf(day) → 0..6`.
  - `tablesForDay(settings, day) → [{seats,count}]`. Uma exceção com `closed: true` dá `[]`. Uma exceção com `tables` substitui o padrão.
  - `slotsForDay(settings, day) → ['HH:MM', ...]`: de `start` até `lastBooking` inclusive, de `slot_minutes` em `slot_minutes`, de todos os turnos do dia da semana, em ordem.
  - `pickTableSize({ tables, reservations, startsAt: Date, durationMinutes, partySize }) → seats | null`. `reservations`: `[{ table_seats, starts_at, ends_at }]`, só as que ocupam mesa. Tamanhos com `seats ≥ partySize`, do menor pro maior. Ocupadas = sobreposição de `[startsAt, startsAt+dur)` com `[starts_at, ends_at)`. Devolve o primeiro tamanho com livre > 0.
  - `availableSlots({ settings, day, partySize, reservations, now }) → [{ time, startsAt, tableSeats }]`. Filtra `startsAt ≥ now + min_advance` e dia ≤ hoje + `max_advance_days`. Grupo acima de `maxParty(settings)` → `[]`.
  - `maxParty(settings) → number`: `settings.max_party` ou o maior `seats`.
  - `occupancyForDay({ settings, day, reservations }) → [{ time, free: { [seats]: n } }]`.

**Interfaces:**

    2. **antes** de enviar, grava a linha `outbound` com `wa_message_id = id`, `sent_by`, `status 'pending'`;
    3. envia com esse id;
    4. em erro, faz `UPDATE status='failed'` e relança.

    Assim o eco do Baileys bate no `ON CONFLICT DO NOTHING` do ingest e não gera linha nova. Com `staff`, o comportamento atual fica igual, mais `sent_by = 'staff'` no INSERT.

    - `isBotPaused(dbImpl, { contactId, now }) → boolean`.
